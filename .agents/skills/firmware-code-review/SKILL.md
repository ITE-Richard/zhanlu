# Code Review

## 必要輸入
- 從 `../../TODO.md` 取得這次變更要解決什麼問題、範圍與完成條件。
- 從 `../../context-index.md` 取得 SPEC、基準版本與相關驗證證據。
- 變更意圖不明時先確認，不把設計爭議直接寫成缺陷。

## 檢查順序
1. 正確性：變更是否真的解決目標問題，是否引入未宣告的行為改變或擴張範圍。
2. 邊界：陣列索引、buffer 長度、整數溢位與型別提升、有號與無號混用、除以零。
3. 併發與時序：ISR 與主迴圈共用資料是否有保護、`volatile` 使用是否正確、critical section 長度、ISR 內是否有阻塞或長時間操作。
4. 硬體互動：register 讀改寫順序、旗標清除方式、等待迴圈是否有逾時、reset 與 power 狀態轉換下的安全性。
5. 資源：ROM／RAM／stack 增量、動態配置、遞迴、過大的區域變數。
6. 錯誤處理：回傳值是否被檢查、失敗路徑是否讓硬體停在安全狀態、是否以關閉 warning 或註解測試換取通過。
7. 可維護性：命名與既有程式碼是否一致、magic number 是否可追溯到 SPEC、是否混入與本 work item 無關的修改。

## 輸出格式
- 每項發現標示：位置、問題、觸發條件、後果、嚴重度。
- 嚴重度分為必須修正、建議修正、僅供參考；偏好不得寫成缺陷。
- 無法只從程式碼判定的項目（實際 timing、實板行為、SPEC 未涵蓋處）標為待驗證，不臆測結論。
- 沒有發現問題時，明確說明審查涵蓋範圍與未涵蓋部分。

## 停止條件
- 審查是分析工作；未取得使用者同意前不直接改寫被審查的程式碼。
- 缺少 SPEC 或基準版本而無法判定正確性時，列為待確認，不以合理推測結案。
