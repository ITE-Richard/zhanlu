# Architecture Design

## 必要輸入
- 從 `../../TODO.md` 取得要解決的架構問題、影響範圍與完成條件。
- 從 `../../project.md` 取得控制器、韌體架構、建置系統與不可修改區域。
- 從 `../../context-index.md` 取得現有程式碼、各專案版本、SPEC 與既有介面的位置。
- 收斂多個既有專案時，先確認每個來源的版本、產品差異與是否仍在量產維護；來源狀態不明時不納入共用基底。

## 方法
1. 先描述現況：目前的分層、相依方向、跨模組耦合點與重複程式碼的實際位置，不以印象代替盤點。
2. 用「會變的」與「不會變的」切界線：晶片相關、板級相關、產品相關與共用邏輯分開。
3. 共用基底只放各專案行為確實一致的部分；行為有差異的留在差異層，不用參數把兩種語意擠進同一個函式。
4. 為每個模組邊界寫下介面契約：呼叫時機、執行 context、是否可阻塞、錯誤回報方式與資料擁有權。
5. 差異化機制優先沿用專案既有做法（board config、Kconfig、feature flag、weak symbol、table-driven），不引入專案沒有的新機制。
6. 評估 ROM／RAM／stack、啟動時間、中斷延遲與可測試性；嵌入式的抽象成本必須算得出來。
7. 提出分階段遷移路徑：每階段可獨立建置與驗證，且可以安全停在中間狀態。

## 停止條件
- 產品差異來自客戶需求而非技術限制時，先取得需求依據，不自行判定哪個行為才是正確的。
- 無法確認某段程式碼為何存在時，不以「看起來重複」為由合併。
- 需求只是分析架構時不直接改寫程式碼；先交付對照與計畫。

## 交付證據
- 現況與目標架構的對照，含相依方向與耦合點。
- 每個模組邊界的介面契約與資料擁有權。
- 差異化機制的選擇理由與資源成本估算。
- 分階段遷移計畫，以及每階段的驗證方式與回退方式。
